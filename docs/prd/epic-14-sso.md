# Epic 14: Single Sign-On for the Management Plane (OIDC)

**Author:** Romain G.
**Target version:** 1.13.0, after Epic 12 Phase 2 (1.12.0) (maintainer decision, 2026-11-14).
**Status:** Reviewed (2026-11-16), written against `main` at `3f224bdc` (v1.10.7); cite function and type names, since line numbers may drift. A requirement challenge, an architecture review against the code and a security review were run on the 2026-11-14 draft; their findings are folded into the decisions and stories below, and the maintainer settled the open choices on 2026-11-16 (D3, D10, D14, D15, Story 14.3 AC6). Claims about third-party identity providers marked *(to verify)* come from their documentation as remembered on the day of writing: those a story depends on are checked before Story 14.1 ("Checks before the first story"), the others by Story 14.4.

*Revised 2026-11-14 (maintainer decision, same day):* the first draft also carried an LDAPS login and examined Kerberos (SPNEGO) in its place. Both are out: the epic is OIDC only, and Windows integrated login is obtained at the identity provider (D14). "Out of scope" records why each was dropped. The same day the maintainer set the target version and the absolute session lifetime (D10).

*Revised 2026-11-16, after review:* the account migration stays additive so the previous release still boots (Story 14.1 AC1); the provider and its settings live in a node-local table of their own, which followers can write (D11); the OIDC endpoints get rate-limit buckets of their own so they can never lock out the break-glass login (D9); SSO accepts RS256 only, so the shared key cache needs no new key type (D3, D13); the return path, the UserInfo fallback and RP-initiated logout are dropped; trust anchors can only be changed from a local session (D15); and the PRD no longer claims MFA it cannot verify (D14).

**Epic Goal:** Let an operator sign in to the Lorica dashboard with the identity they already have, through an OpenID Connect provider (authentik, Keycloak, AD FS, Entra ID, any conformant one), with their Lorica role derived from their group membership. Joining or leaving the operations team becomes a change at the identity provider, not a ticket to whoever holds the Lorica SuperAdmin password.

**What this epic is not:** it is not about the traffic Lorica proxies. Protecting a proxied application behind authentik or Keycloak is forward authentication, shipped in v1.3.0 (`lorica/src/proxy_wiring/forward_auth.rs`) and unchanged here. It is not about CI either: the GitLab OIDC ID tokens of Story 10.5 authenticate a pipeline on the automation listener, a different plane with a different caller. This epic is the human login to the management plane.

## What exists today

- **Accounts are local.** `lorica_config::models::User` carries a username, an Argon2id hash (`lorica-api/src/auth.rs`, `argon2_hasher`), one `Role` and a `disabled_at`. `User::password_hash` is a `String` and `users.password_hash` is `NOT NULL`; `row_to_user` (`lorica-config/src/store/row_helpers.rs`) reads it as such. Usernames are 3 to 32 characters, lowercase alphanumeric plus `._-`, a rule of `POST /api/v1/users` (`validate_username`, `lorica-api/src/users.rs`), not of the table: `ensure_admin_user` and the config import insert without it. The first boot creates `admin` with a random password and `must_change_password`.
- **Three roles.** `Viewer`, `Operator`, `SuperAdmin` (`lorica-config/src/models/enums.rs`), ordered, with the whole authorization matrix in `required_role` (`lorica-api/src/middleware/authorize.rs`). The users CRUD keeps one invariant: the last enabled SuperAdmin cannot be demoted, disabled or deleted (`count_active_super_admins`).
- **Sessions.** `POST /api/v1/auth/login` issues `lorica_session`, `HttpOnly; Secure; SameSite=Strict; Path=/api` (`session_cookie`, `lorica-api/src/middleware/auth.rs`). A session expires after 30 minutes without a request (`SESSION_TIMEOUT_MINUTES`) and is renewed by every authenticated request, with **no absolute lifetime**; the dashboard polls on many pages, so an open tab never reaches the idle expiry. Sessions persist in SQLite and survive a restart. The role is denormalised onto the session at login (migration 46, `migrate_session_role`), which is safe because a role change, a disable or a password reset removes every session of the account (`update_user`, `remove_all_for_user`).
- **The listener.** The management API binds to loopback, port 9443 by default, over TLS (`docs/security.md`, "Management plane authentication"). Operators reach the dashboard through an SSH tunnel or a fronting reverse proxy, which may be Lorica itself. The node therefore does not know the URL the browser uses. The dashboard is served at the root of its origin and calls `/api/v1` absolutely, so it cannot live under a path prefix.
- **Login hygiene.** A rate-limit bucket named `login`, 5 attempts per 60 s keyed by the TCP peer address (`RateLimiter`, `lorica-api/src/middleware/rate_limit.rs`); behind a tunnel or a fronting proxy on the host every client is `127.0.0.1`, so in practice it is one bucket per node. A dummy Argon2 verify on an unknown username so timing does not reveal which usernames exist, and a deliberate choice not to audit failed logins (`login`, `lorica-api/src/auth.rs`).
- **Accounts never replicate.** `docs/cluster.md`: users, sessions and preferences stay node-local; a compromised control plane cannot push an account to an edge. They do travel through the config export and import (`lorica-config/src/export.rs`, `import.rs`): export writes every user with the hash redacted, import refuses a redacted hash, clears the store and recreates every row.
- **Followers are read-only.** On a follower, every non-GET request outside the paths `follower_local_request` admits answers 409 unless break-glass is open (`follower_read_only`, `lorica-api/src/middleware/authorize.rs`). The AD CS authority of Epic 13 shows the pattern for node-local configuration: its own table (migration 64, `migrate_adcs_authority`), no field in the replicated settings, none in `ExportData`.
- **The CLI logs in with a password.** Every `lorica` subcommand that talks to the local management API takes a username and a password and pins the served certificate (`served-cert.pem`).
- **OIDC building blocks already in the tree.** Story 10.5 verifies JWTs with `jsonwebtoken` (algorithm pinned before any key lookup, `OIDC_CLOCK_SKEW_SECONDS` of 60) and caches key sets behind the `JwksFetcher` trait (`lorica-api/src/automation/oidc/jwks.rs`). That cache keeps RSA keys published for `RS256` only (`rsa_keys_by_kid`), refreshes every 6 hours (`JWKS_REFRESH_INTERVAL`), is typed on the automation model (`decoding_key_for(&OidcIssuer, ..)`) and counts its fetches in an automation metric (`inc_automation_oidc_jwks_fetch`). Outbound HTTP starts from `lorica_tls::http_client`, the only place `clippy.toml` lets a reqwest client or a rustls `ClientConfig` be built; that module gives the TLS policy, and each caller sets https-only, the redirect policy, timeouts and body caps (as `jwks.rs` does with `same_origin_redirects`). Secrets are stored in encrypted columns registered in `ENCRYPTED_COLUMNS` (`lorica-config/src/store/mod.rs`). `ring`, `base64` and `rand` are already dependencies of `lorica-api`.
- **No second factor.** Lorica has no TOTP or WebAuthn. A provider can require one for the dashboard's client; Lorica cannot see whether it did (D14).

## Decisions taken up front

**D1 - OIDC Authorization Code flow with PKCE, confidential client, and nothing else.** Lorica is a relying party registered as a confidential client with a client secret, and uses PKCE `S256` on top. No implicit flow, no hybrid flow, no resource-owner password grant. The ID token is accepted only from the token endpoint's response, never from a URL or a form: that back-channel delivery over TLS is the first guarantee of the token's origin (OIDC Core 1.0, 3.1.3.7), and the signature checks of D3 are defence in depth on top of it. OIDC is the only protocol Lorica speaks for human login; "Out of scope" records why SAML, LDAP and Kerberos are not added beside it.

**D2 - The provider is configured by its issuer, the issuer is pinned, and its endpoints cannot move silently.** The SuperAdmin enters the issuer URL, the client id and the client secret. Lorica reads `/.well-known/openid-configuration`, requires `https`, and requires the document's `issuer` to equal the configured one byte for byte. Every endpoint the document names (authorization, token, JWKS, end-session) must be `https`, or the document is refused. The endpoints read at save time are stored with the provider and shown by the connection test. Discovery is re-read on a bounded schedule to detect change, not to follow it: a refresh in which the issuer or the origin of any endpoint differs from the stored snapshot refuses SSO logins, logs at ERROR and raises the provider's status in the settings page until a SuperAdmin saves the provider again. Outbound calls set their own policy on top of `lorica_tls::http_client`: a connect and a total timeout and a body cap on every call; discovery and JWKS follow same-origin redirects only, as Story 10.5 does; the token endpoint, which receives the client secret, follows no redirect at all. An optional CA bundle pins the provider's TLS trust for every one of these calls, with the same rule as Story 10.5's `ca_pem`: when set, it alone is trusted.

**D3 - ID token validation is strict, RS256 only, and the algorithm never comes from the token.** The only accepted algorithm is `RS256` (maintainer decision, 2026-11-16): it is the default of every provider D14 names once a signing key is configured, and it is what the shared key cache already holds (D13). The provider's `id_token_signing_alg_values_supported` must contain it. Validation:
- the header's `alg` is checked against the allowlist before any key lookup; `kid` is required; the key comes from the cached JWKS only, and the `jku`, `x5u`, `jwk` and `x5c` header parameters are ignored; the key must be RSA, with `use` absent or `sig`, and `alg` absent or `RS256`;
- `iss` equals the configured issuer; `aud` contains the client id, and a token with several audiences must carry `azp` equal to the client id; `azp`, when present, equals the client id;
- `exp` and `iat` are checked with the clock skew Story 10.5 uses (`OIDC_CLOCK_SKEW_SECONDS`), and `iat` is no older than the flow lifetime of D4 plus that skew;
- `nonce` is required and equals the flow's, compared in constant time.

**`HS256` is refused**, and so is every other algorithm. An HMAC-signed ID token would make verification depend on a secret Lorica stores, and would offer no protection the day the token endpoint's TLS is intercepted (a TLS-inspecting proxy, a wrong CA pin), which is the case the signature exists for. authentik signs with the client secret when no signing key is selected on the provider *(to verify before Story 14.1)*; `docs/sso.md` tells the operator to select one, and the connection test (Story 14.2) reports the case by name. Claims are taken from the ID token only: Lorica never calls the UserInfo endpoint. Every provider in D14 can place the groups in the ID token, and each recipe in `docs/sso.md` says how.

**D4 - The flow state lives on the server, in memory, and the browser starts it with a same-origin request.**
- **Start.** The login page sends `POST /api/v1/auth/oidc/start` with `fetch`, same-origin; the management API has no CORS layer, so no other site can send it. The answer is `200 {"authorization_url": ...}` with the flow cookie set, and the page navigates to the URL with `window.location`, not through a form (the dashboard CSP carries `form-action 'self'`, which engines may apply to the redirect that follows a form).
- **The pending flow.** It holds `state`, `nonce`, the PKCE verifier, the provider id and the issuer the flow was started for. Flows live in a bounded in-memory map in the supervisor, are not persisted, live 10 minutes and are single-use. A full map evicts its oldest flow rather than refusing a new one, and evictions are counted, as `ReplaySet` does for automation tokens; a restart or a hot upgrade invalidates the flows in progress, which costs the user one click (accepted). The flow id, `state`, `nonce` and the PKCE verifier are four independent CSPRNG values of at least 128 bits each; the flow id never appears in a URL.
- **The flow cookie.** `__Host-lorica_oidc_flow`, `HttpOnly; Secure; SameSite=Lax; Path=/`, no `Domain`, so a sibling host under the same registrable domain cannot plant one. `Lax` is required because the provider returns the browser through a cross-site top-level `GET`, which a `Strict` cookie does not accompany. The callback refuses a request that carries no flow cookie or more than one.
- **The callback.** `GET /api/v1/auth/oidc/callback`, with `response_mode=query` pinned at start (a `form_post` return is a cross-site POST, which a `Lax` cookie does not accompany). When the response carries the RFC 9207 `iss` parameter it must equal the flow's issuer, and it is required when discovery advertises `authorization_response_iss_parameter_supported`. The callback always answers `303 Location: /`: there is no server-side return path, because the dashboard routes on the URL fragment, which the server never sees, and an echoed return path is an open-redirect surface. The login page keeps the route it wants in `sessionStorage` before starting and restores it after the boot probe. The start and callback responses carry `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.
- **The session cookie stays `Strict`.** The callback is a top-level navigation, whose response may set it; the `303` to `/` does not need it (`Path=/api`); the dashboard's boot probe `GET /api/v1/auth/me` is a same-origin request from the loaded document and carries it. Story 14.3 pins this sequence in two real browsers, because it is the kind of claim that is true in one engine and false in another.

**D5 - Lorica needs to be told its public URL, and it is an origin.** The redirect URI is `<management_public_url>/api/v1/auth/oidc/callback`, where `management_public_url` is the origin the operator's browser uses to reach this node's dashboard. It is validated on write: `https` scheme, a host, an optional port, no userinfo, no path, query or fragment, stored without a trailing slash, an IDN host stored in its ASCII form; anything else is refused, with vector tests. Lorica never derives it from the `Host` or `X-Forwarded-*` headers of the request, which a client controls. OIDC cannot be enabled while it is empty. Cookies are bound to the host, so SSO only works from that origin: the login page shows the SSO button only when `window.location.origin` equals it, and otherwise says at which address SSO is available. A node reached through a fronting proxy has its own origin; nodes reached through an SSH tunnel are all `https://localhost:<port>` to the browser, so they share a redirect URI and every operator must tunnel on the registered local port. The value lives on the provider row (D11), not in the global settings.

**D6 - Groups decide the role, matched exactly, and no group means no access.** The provider carries a set of mappings from a group value, read from the configured claim (default `groups`), to a `Role`. Values are non-empty and compared byte for byte: no case folding, no wildcard, no prefix. The effective role is the highest role any matching mapping grants (`Role` is ordered, so it is a maximum, and the order of the mappings means nothing). **A user who matches no mapping is refused**, with a message saying so; there is no default role, because `Viewer` already exposes the backend topology and the certificate inventory. The role-mapping function is pure and tested on its own. Mapping values must be identifiers only an administrator controls: on Entra ID, where display names are not unique and users may be allowed to create groups, a group object id or, preferably, an app role (`roles` claim); a Keycloak full group path; an AD FS group SID or a claim rule restricted to named groups; an authentik group. The settings page warns when the issuer is Entra ID and a mapping value is not a GUID, and `docs/sso.md` states that the groups claim must not be one the end user can edit.

**D7 - External accounts are provisioned on first login, identified by issuer and subject, and never linked to a local one.** A successful SSO login with a mapped role creates or updates a `User` row with `auth_source` (`local`, `oidc`), the provider id, the issuer and the `sub` claim. The account is found by `(issuer, sub)` only: `sub` is unique within an issuer, not across them, and the username is never used to find a row. Lorica never attaches an external identity to a local account by matching a username or an email address, which is the classic account-takeover path. The username is a display value taken from a configured claim (default `preferred_username`), refreshed at each login, with no fallback to another claim: an absent claim, or one that is empty, too long or carries a control character, refuses the login (`username_invalid`). External usernames are NFC-normalised and follow a wider character set than local ones (`@` for UPNs and emails), still bounded in length. A username already held by any other row, whatever its source or provider (compared case-insensitively), refuses the login (`username_collision`); the browser gets a generic "account name conflict, contact your administrator", and the colliding row goes to the server log only, so the refusal cannot enumerate local accounts. The authentik recipe requires a subject mode based on the hashed user id, so `sub` does not change with the username *(to verify before Story 14.1)*.

**D8 - The role of an external account belongs to the provider; its access can still be cut in Lorica.** The role is recomputed at every login. The API refuses a `role` or a `password` in `PUT /api/v1/users/{id}` for an external row, and the users page shows the role read-only; the password change and reset paths refuse external rows too. When a login computes a role different from the stored one, every other session of the account is removed before the new one is created, and the change is audited as `user.update`. A login refused for `no_role_mapping` or `disabled` on an existing row removes that row's sessions. A SuperAdmin can **disable** an external account, which takes precedence over the provider and removes its sessions. An **enabled** external account can be deleted, which only removes the row: it is provisioned again at its next successful login, and the users page says so. A **disabled** external account cannot be deleted, because deleting the row would delete the disable and let the account back in at its next login; re-enable it first, or leave it disabled.

**D9 - A local SuperAdmin always remains: break-glass is permanent.** The last-SuperAdmin invariant counts **enabled local** SuperAdmins, through the users CRUD and through the config import, which refuses a file that would leave none. An outage of the provider, an expired client secret or a broken group mapping must never lock the operator out of the node that would fix it, and the CLI, which authenticates with a password (see "What exists today"), keeps a working account. Password login stays available on the login form; restricting it is out of scope. The OIDC endpoints never consume the `login` rate-limit bucket: start, callback and the public configuration endpoint each have a bucket of their own, so no amount of SSO traffic, legitimate or not, can refuse the password login.

**D10 - External sessions have an absolute lifetime of 4 hours.** A session opened through OIDC keeps the 30-minute idle expiry and ends at the latest 240 minutes after it was created. Four hours is the maintainer's choice for a plane that grants administrative rights and is used occasionally (2026-11-14), and it is a constant, not a setting (2026-11-16): the cost of a short lifetime is low, because while the provider's own session is alive a new login is a redirect with nothing to type. The absolute expiry is fixed when the session is created. A user removed from the provider, or from the group that granted the role, loses access at the latest when that lifetime ends, and at once on the triggers of D8 and D11. Revocation pushed by the provider (back-channel logout) is deferred. Local sessions keep today's behaviour in this epic; the weaknesses the review found in it are backlog #96.

**D11 - One provider per node, in a node-local table, SuperAdmin-only.** An identity provider is a trust anchor that decides who becomes SuperAdmin, so it follows the users it creates: node-local, never replicated (the `docs/cluster.md` rule for accounts), and administered by SuperAdmin only, every change audited. It lives in a table of its own, following the migration-64 precedent of the AD CS authority: one row holding the issuer, client id, client secret (encrypted), token endpoint authentication method, display name, `management_public_url` (D5), scopes, username and groups claims, role mappings, optional CA bundle, the endpoint snapshot of D2 and the enabled flag. The table is absent from the replicated configuration and from `ExportData` by construction, and is left untouched by an import; nothing is added to `GlobalSettings`, so the settings API, the replication of settings and the automation read plane do not see it. The store refuses a second row. On a fleet each node is configured on its own, including on a follower, whose read-only gate admits the provider paths (Story 14.2). Any write that changes the issuer, the client id, the groups claim, the role mappings or the enabled flag, and the deletion of the provider, removes every session opened through it, in the same request. External rows are keyed by issuer (D7), so after an issuer change the old rows match no new login; they stay in the users page until deleted. The model keeps a provider id so a later release can add several providers without a migration.

**D12 - Logins are audited whatever the source; failures are counted, and audited once the identity is proven.** A successful SSO login records `auth.login` with `after = {method: "oidc", provider_id, issuer, subject, username}`: the audit context identifies an actor by username only, and an external username is provider-controlled and may be reused, so the subject in the login row is what lets an auditor resolve later rows. The local login row is left as it is. The first login of an external identity records `user.create` with the provider named as creator, because a SuperAdmin appearing without any SuperAdmin action is the event an auditor looks for; a role change at login records `user.update` (D8). Every login attempt is counted in `lorica_auth_logins_total{method,outcome}`, the local one included, so `/metrics` changes even on a node with no provider. The outcome set is one Rust enum (`success`, `bad_credentials`, `flow_invalid`, `provider_error`, `token_invalid`, `groups_claim_invalid`, `no_role_mapping`, `username_invalid`, `username_collision`, `disabled`), and the metric registration, the login page messages and `docs/sso.md` are derived from it, per `.claude/rules/derived-not-transcribed.md`. Failures before a valid ID token (`flow_invalid`, `provider_error`, `token_invalid`) keep today's rule: logged with their outcome, not written to the audit chain, which an attacker could otherwise grow. Failures after it (`groups_claim_invalid`, `no_role_mapping`, `username_invalid`, `username_collision`, `disabled`) concern an identity the provider has authenticated, and are audited as `auth.login_refused`. A `no_role_mapping` refusal logs at WARN the claim name and the values it carried, so a SuperAdmin can fix the mapping from the log. Every provider-supplied string (usernames, group values, error codes) is stripped of control characters before it reaches a log line, a message or an audit row.

**D13 - No new runtime dependency, no new crate.** `jsonwebtoken`, `ring` (SHA-256 for PKCE), `base64`, `rand` and the shared reqwest client cover the relying party. It lives in `lorica-api` under `src/sso/`, next to the sessions it creates; a separate crate would need a trait for each of its collaborators (`SessionStore`, `AppState`, `audit::record`, `RateLimiter`, the users store) and the full new-crate checklist of `lorica-rust.md`, for no isolation the module boundary does not already give. The JWKS cache of Story 10.5 moves to `lorica-api/src/oidc/`, a module both planes use and neither owns, and `automation::oidc` re-exports it so every existing path and test compiles unchanged. The move generalises it without changing what the automation listener accepts:
- a `KeySource` trait (a cache id, the JWKS URL, an optional CA bundle) implemented by the automation issuer and by the provider, in place of `&OidcIssuer`;
- the fetch outcome reported through a recorder each caller injects, so `automation_oidc_jwks_fetch_total` keeps its exact series and SSO gets its own;
- the cache slot and the pinned client keyed by a digest of the CA bundle as well as the id, because the provider is editable and a CA change must not leave the old client in use (automation issuers are create and delete only, which is why this never mattered);
- one cache instance per plane, so no throttling window or failure grace crosses from one to the other, and a refresh interval per instance: 1 hour for SSO, so a key the provider withdrew stops verifying sooner; 6 hours for automation, unchanged.

Both planes accept RS256 RSA keys only (D3), so the key extraction itself does not change. The browser test of Story 14.3 AC7 adds browser automation to the e2e image: a test-only dependency, kept by the maintainer over a manual check (2026-11-16).

**D14 - Windows integrated login happens at the identity provider, not in Lorica, and so does MFA.** An operator on a domain-joined workstation gets a login without typing anything when the provider performs Kerberos on the intranet and then hands Lorica an ID token: AD FS with Windows Integrated Authentication, Entra ID with Seamless SSO, authentik with its Kerberos source (documented as available since 2024.10.0 and marked Preview; whether it is still Preview in the release checked by Story 14.4 is *to verify*) in front of an LDAP or Kerberos source that reads Active Directory. The provider also resolves the AD groups and puts them in the token, so Lorica needs neither a keytab, a service principal, a DNS name in the realm, nor a directory connection. The cost, accepted by the maintainer: an Active Directory estate with no OIDC provider at all must deploy one (authentik, Keycloak or AD FS) to use SSO on Lorica; until then it keeps local accounts. **Lorica does not verify a second factor** (maintainer decision, 2026-11-16): it sends no `acr_values` and checks neither `acr` nor `amr`. Whether a login to the dashboard required MFA is decided by the provider's policy for Lorica's client, and integrated Windows login usually satisfies a login with the workstation's ticket alone. The settings page and `docs/sso.md` say so in those words; requiring an `acr` value is backlog #97.

**D15 - Trust anchors can only be changed from a local session.** A session carries its source (`local`, `oidc`). A session opened through SSO, whatever its role, is refused (403, with an error naming the requirement) on every write that would let a compromised provider keep its foothold after it is cleaned up: creating a local account, changing the role of, resetting the password of, disabling or deleting a local account; any write to the identity provider, which carries the public URL (D11); minting or revoking an automation token, and any write to the automation OIDC issuers of Story 10.5. These need a session opened with a local password. An SSO SuperAdmin keeps every other right, including the management of external accounts. With D15, a compromised provider grants SuperAdmin on the dashboard for as long as its sessions live (at most D10's 240 minutes after the provider is disabled, at once with D11's revocation), but no way to plant a local account, a token or a different provider that would outlive the clean-up.

## Checks before the first story

Done by the maintainer on their authentik before Story 14.1 is drafted, outcome written in "Delivery notes":
1. With a signing key selected on the provider, the discovery document's `id_token_signing_alg_values_supported` contains `RS256`, and an ID token carries `alg: RS256` (D3); without one, the token is `HS256` (the case the connection test names).
2. A subject mode based on the hashed user id gives a `sub` that does not change when the username does (D7).
3. The groups reach the ID token itself, with a scope mapping and no UserInfo call (D3).

If any of these fails, D3 or D7 is revisited before a line of code depends on it.

## Story 14.1: External identities in the account model

As a SuperAdmin,
I want the account model to know where an identity comes from,
so that SSO users get sessions, roles and audit entries like local ones without weakening the local accounts.

### Acceptance Criteria

1. **Additive migration** (number following the last entry of `MIGRATIONS` in 1.12.0). `users` gains `auth_source TEXT NOT NULL DEFAULT 'local'`, `provider_id`, `issuer` and `external_subject` (all `DEFAULT NULL`), added with `add_column_if_absent`, and a unique index on `(issuer, external_subject)` (SQLite admits several NULL pairs, so local rows do not collide). `password_hash` stays `NOT NULL` and no table is rebuilt: an external row stores the Argon2id hash of 32 random bytes generated at provisioning and discarded at once, never `DUMMY_PASSWORD_HASH`, whose plaintext is in the source tree. The invariant (a row is `local` if and only if it has no subject; `auth_source` in the closed set) is enforced by the store's write methods. `sessions` gains `auth_source`, `provider_id` and `absolute_expires_at`, the same way.
2. **The local login path refuses external rows**: it runs the same Argon2 verification as for any account, then refuses an external row with the same generic `invalid credentials`, as it does for a disabled account. `PUT /api/v1/users/{id}` refuses `role` and `password` for an external row, and the password change and the admin reset refuse them, each with an explicit error (D8); tested through the API, not the page.
3. **Role mapping function** (D6), pure, in `lorica-api/src/sso/`, with vector tests: highest role wins, no match refuses, empty mapping set refuses, duplicate values, a value differing only in case does not match.
4. **Break-glass invariant** (D9): demoting, disabling or deleting the last enabled **local** SuperAdmin is refused whatever the number of external SuperAdmins, tested through the users CRUD; an import that would leave no enabled local SuperAdmin is refused, tested through the import.
5. **Absolute session lifetime** for external sessions (D10). The invariant `expires_at <= absolute_expires_at` whenever the latter is set: `create` sets both, `renew` writes the minimum of the idle expiry and the absolute one, so `get` (cache and database fallback), `purge_expired`, `cleanup_expired_sessions`, the restore at restart and `/auth/me` need no new predicate. `get_session` and `load_all_sessions` return a named `StoredSession` in place of their tuples, carrying the source, provider and absolute expiry, so a renewal after a restart or a database fallback still caps.
6. **Users page**: source, provider and issuer shown; role read-only for external rows; disable for any row; delete refused for a disabled external row, with the D8 wording on the delete of an enabled one.
7. **Audit and metrics** per D12.
8. **Export and import.** External rows are left out of the export (they are provisioned again at their next login); an import refuses a row whose `auth_source` is not `local`; the new `User` fields carry `#[serde(default)]`, so an export written by an earlier release still imports, as local accounts; `user_eq` compares `auth_source`.
9. **Trust-anchor gate** (D15): every write it lists is refused to an SSO session and accepted from a local one, one test per path family.

### Integration Verification

- IV1: Every existing login, session and users-CRUD test passes with constructor-only edits (the new `Session` and `User` fields), no assertion changed.
- IV2: A database upgraded from 1.12.x, and those built from the upgrade fixtures in `lorica-config/tests/fixtures`, keep their accounts, all `local`, and log in with the same passwords.
- IV3: A database holding an external row and an SSO session boots on 1.12.x and lists its users. The downgrade semantics are recorded in the release notes: on the previous release an external row looks like a local account nobody knows the password of, and an admin reset there turns it into a working local one; SSO sessions lose their absolute bound, so the downgrade procedure removes the sessions of source `oidc` first and disables the external rows.

## Story 14.3: Signing in with OIDC

As an operator,
I want a "Sign in with <provider>" button on the login page,
so that I reach the dashboard with my organisation's identity, under whatever login policy my organisation applies to it.

### Acceptance Criteria

1. **`GET /api/v1/auth/oidc/config`**, public, behind its own small bucket: enabled flag, display name and public origin, nothing else; with no provider it answers "disabled" and the login page is unchanged (NFR1). The page shows the button per D5.
2. **`POST /api/v1/auth/oidc/start`** per D4: its own rate-limit bucket, never `login`; creates the pending flow, evicting the oldest when the map is full; sets the flow cookie; answers `200` with the authorization URL carrying `response_type=code`, `response_mode=query`, `state`, `nonce`, `code_challenge` (`S256`), the configured scopes and the D5 redirect URI.
3. **`GET /api/v1/auth/oidc/callback`**, its own bucket: requires exactly one flow cookie, the matching `state` and an unexpired, unused flow; consumes the flow before anything else; checks the RFC 9207 `iss` parameter per D4; exchanges the code with the PKCE verifier (no redirect followed); validates the ID token per D3; resolves the role per D6; finds or provisions the account per D7; applies the revocations of D8; refuses a disabled account; creates the session (D10); answers `303 Location: /` with the D4 headers. After the flow is consumed, the work runs as one `management_units()` unit, because a GET escapes `detach_mutations` and a client hanging up must not lose the audit row; no store lock is held across an outbound call.
4. **Errors**: a provider error (`error=access_denied` and others) and every refusal land on `/?sso_error=<outcome>`, with the outcome from the D12 enum; the login page maps it to a message derived from the same enum and clears the query with `history.replaceState`. The provider's raw text is never shown.
5. **Groups claim edge cases**: a claim that is absent, not an array of strings, or an Entra ID overage indicator (`_claim_names`) refuses the login with `groups_claim_invalid`; Lorica does not call Microsoft Graph.
6. **Logout** is local, as today. RP-initiated logout is deferred (out of scope).
7. **Browser end-to-end test** of D4 in Chromium and Firefox: start, provider login, callback, dashboard loaded with the role, refresh keeps the session, the flow cookie is gone. WebKit is recorded as untested.
8. **Secrets** (NFR3): a test drives a full login and greps the logs, every API response and the audit rows for the client secret, the authorization code, the ID token and the PKCE verifier.

### Integration Verification

- IV1: Each of these is refused, one test per case: a replayed callback URL; `state` swapped between two flows; no flow cookie; two flow cookies; a wrong or missing `nonce`; a wrong `aud`, `iss` or `alg`; an `HS256` signature; an `exp` in the past; an `iat` older than the flow lifetime; several audiences without `azp`; a `jku` header pointing elsewhere; an unknown `kid`; an RFC 9207 `iss` that differs from the flow's; a username held by another row, local or external; an absent username claim.
- IV2: The local password login works with OIDC enabled, disabled and with the provider unreachable, and right after the start and callback buckets have been exhausted.
- IV3: A login that maps a lower role removes the account's other sessions; disabling the provider removes every session it opened.

## Non-functional requirements

- **NFR1 - No change for an operator who configures nothing.** With no provider configured, the login page, the API and every existing test behave as in the previous release. The one visible difference is the `lorica_auth_logins_total` series, which counts local logins too (D12).
- **NFR2 - A provider outage never reaches the data plane** and never blocks a local login. Every outbound call is bounded in time and size (D2).
- **NFR3 - No secret in Lorica's logs, API responses or audit rows**: client secret, authorization code, ID token, PKCE verifier (Story 14.3 AC8). A fronting proxy's access log is outside this guarantee and documented (Story 14.4 AC3).
- **NFR4 - Quality gates** as CI runs them (`lorica-rust.md`, `lorica-frontend.md`), coverage of the new modules at or above the project baseline.

## Out of scope

- **SAML.** Refused. Every provider named here also speaks OIDC, and SAML would bring XML signature verification, a parser surface with a long defect history, for no estate OIDC does not already cover.
- **LDAP or LDAPS login in Lorica.** Dropped from the first draft. It is centralised credentials rather than single sign-on (the directory password is typed into Lorica), it needs a new dependency, a service account, and a lockout guard so Lorica cannot be used to spray passwords against Active Directory. Every OIDC provider in D14 already reads the directory and puts the groups in the token.
- **Kerberos (SPNEGO) in Lorica.** Examined and refused in favour of D14. In Lorica it would need a keytab per node for an `HTTP/` service principal and its rotation, a DNS name in the realm (the loopback listener reached through an SSH tunnel cannot carry it), no TLS channel binding behind a terminating proxy, an LDAP lookup anyway because a ticket carries no usable group list without decoding the PAC, and a second login method for every workstation outside the domain. The provider does the same at no cost to Lorica.
- **Algorithms other than RS256** (D3). Adding one means a key filter per caller in the shared cache and key-binding rules per key type.
- **The UserInfo endpoint** (D3). Groups come from the ID token.
- **A return path after login** (D4). The dashboard restores its route itself.
- **Several providers per node.** D11. The model keeps the id, and the flow already records its provider and issuer; several providers will also need a redirect URI per provider or the RFC 9207 `iss` parameter made mandatory, against the mix-up attack.
- **Replicating the provider across the fleet.** D11.
- **RP-initiated logout** (maintainer decision, 2026-11-16). It would mean keeping each session's ID token for `id_token_hint`, or relying on the provider's confirmation prompt with `client_id`. After a Lorica logout the provider session survives, and the next sign-in is a redirect.
- **OIDC back-channel and front-channel logout, refresh tokens.** D10 bounds the exposure instead.
- **Verifying MFA** (`acr`, `amr`). D14; backlog #97.
- **`private_key_jwt` client authentication.** The RFC 9700 recommendation; a later option beside the client secret.
- **SSO for the CLI** (device authorization grant). The CLI keeps local accounts (D9).
- **SSO for the automation listener and MCP.** Automation tokens and Story 10.5's ID tokens are unchanged.
- **SCIM provisioning and deprovisioning.** Accounts appear at first login and lose access through D8, D10 and D11.
- **Restricting or hiding the password form.** D9.
- **A local second factor (TOTP, WebAuthn).** A separate decision for local accounts.
- **Local session hardening** (session ids stored raw, renewal by background polling, no absolute lifetime for local sessions, a `__Host-` session cookie). Found by the review, not caused by this epic; backlog #96.
