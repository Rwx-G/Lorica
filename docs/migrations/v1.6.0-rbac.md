# v1.6.0 migration: multi-user RBAC

Author: Romain G.

## What changes

v1.6.0 replaces the single-admin login with role-based team accounts
(Story 8.3). Three built-in roles:

| Role | Can do |
|---|---|
| `super_admin` | Everything: settings, DNS providers, notification configs, cert-export ACLs, config import, binary upgrades, user management |
| `operator` | Full CRUD on routes, backends, certificates, WAF, SLA, probes, load tests, cache, bans; read-only on settings; no user management |
| `viewer` | Read-only on everything; secrets (certificate private keys, SMTP passwords, webhook URLs, DNS tokens) are scrubbed or blocked |

## Automatic migration of the existing admin

On first start of v1.6.0, the database schema migrates automatically
(schema version 22): the `admin_users` table is replaced by a `users`
table and the existing `admin` row is carried over unchanged as a
`super_admin` account. The password hash migrates as-is: you keep
logging in with the same username (`admin`) and the same password,
nothing to do. Existing dashboard sessions survive the upgrade;
they are treated as super-admin sessions (they could only belong to
the single admin) and expire on their normal 30-minute sliding
window.

## API compatibility

- `POST /api/v1/auth/login` still accepts the pre-1.6.0 body shape
  `{"password": "..."}`; it routes to the `admin` account. The new
  shape is `{"username": "...", "password": "..."}`.
- Pre-1.6.0 TOML config exports still import: the legacy
  `[[admin_users]]` section maps onto `users` with
  `role = "super_admin"`.
- New endpoints: `GET /api/v1/auth/me` (identity + role behind the
  session) and `/api/v1/users` CRUD (super-admin only).

## Password policy

Passwords SET after the upgrade (change-password, user creation,
admin resets) must be at least 14 characters with one uppercase, one
lowercase, one digit, and one symbol. Existing passwords keep
working for login; the policy only applies when a password changes.
Tunables: `password_min_length` and `password_require_complexity`
in global settings.

## Creating team accounts

Dashboard: Settings -> Users & access (visible to super admins).
API: `POST /api/v1/users` with `{"username", "password", "role"}`.

Safety rails: the last enabled super admin cannot be demoted,
disabled, or deleted; you cannot delete your own account; any role
change, disable, or password reset logs the target out of every
active session immediately.
