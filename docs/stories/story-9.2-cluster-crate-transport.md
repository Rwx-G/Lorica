# Story 9.2: `lorica-cluster` Crate, Transport and Listeners

**Epic:** 9 (v1.7.0)
**Status:** Review
**Author:** Romain G.

**Depends on:** Story 9.1 (all of it).

## Story

As an infrastructure engineer,
I want a dedicated cluster plane that carries authenticated, encrypted
traffic between a control-plane node and its followers,
so that fleet coordination never rides on the loopback-only management
API and never forces a follower to expose an inbound port.

## Acceptance Criteria

1. New workspace crate `lorica-cluster`. Workspace `Cargo.toml`
   `members`; `COPY lorica-cluster/ lorica-cluster/` in **all three**
   Dockerfiles; `docs/BUMP-CHECKLIST.md`; cross-deps in `lorica`,
   `lorica-api`, `lorica-config`. `#![deny(unsafe_code)]` and
   `#![warn(missing_docs)]` at the crate root.
2. Two distinct listeners. The **operational** listener requires client
   authentication: a new rustls `ServerConfig` with
   `WebPkiClientVerifier` **without** `allow_unauthenticated`. The
   **enrollment** listener is separate, accepts peers holding no
   certificate, is off unless at least one join token is live, and
   auto-closes when the last unexpired token is burned or expires. It is
   the only unauthenticated surface in the product and is documented as
   such.
3. Pre-authentication budgets on the enrollment listener, enforced
   before any token verification: handshake timeout, max concurrent
   handshakes, max in-flight enrollments, per-connection byte and time
   budget. Exceeding any drops the connection and increments a counter.
4. Protocol version negotiation uses a minimum-compatible-version range,
   not exact equality. The version exchange happens after
   client-certificate verification on the operational path; the
   enrollment path returns an opaque code on the wire and logs the
   diagnostic locally.
5. The handshake also exchanges `schema_version()`. A follower below the
   control plane's schema refuses configuration apply with a distinct
   diagnostic.
6. Cluster messages are a disjoint type in a separate proto package. The
   bridge into `lorica-command` is an explicit whitelist translation
   with no pass-through of a peer-supplied `CommandType`. A cluster
   message that decodes as a worker command drops the connection.
7. Telemetry never shares queue budget with configuration: separate
   multiplexed streams with separate credit, or a separate connection.
8. Cluster CA generated by `lorica cluster init`, persisted through the
   existing AES-256-GCM helpers. The story documents that the CA key
   inherits the existing master-key trust model.
9. Follower dialer: long-lived outbound connection, mutual TLS,
   heartbeat, reconnect with exponential backoff and jitter whose cap
   scales with fleet size, accessed through an `ArcSwap`.
10. Control-plane admission control on convergence: a concurrent-session
    limit with a queue and a `RETRY_LATER` response.
11. `--cluster-listen` takes an explicit `host:port`. A bare port is
    refused, `0.0.0.0` / `::` refused unless a separate explicit flag is
    present, a bind equal to the management port refused, effective bind
    logged at WARN.
12. Prometheus: `lorica_cluster_connection_state{node_id, state}`,
    `lorica_cluster_rpc_total{direction, method, outcome}`,
    `lorica_cluster_rpc_duration_seconds`. Labels use server-side
    `node_id` only, never the follower-supplied `node_name`.

## Dev Notes

**AC #2 exists because the first PRD draft was internally
contradictory.** It claimed `WebPkiClientVerifier` rejects unenrolled
peers at the handshake while also requiring an enrollment flow for nodes
that have no certificate yet. Those are mutually unsatisfiable on one
listener. Two listeners is the resolution; the enrollment one is
genuinely unauthenticated and must be treated as such.

**The existing mTLS helper is not reusable.** `build_verifier` hardcodes
`.allow_unauthenticated()` (`lorica/src/mtls.rs:99`), meaning a peer with
no client certificate completes the handshake and enforcement is
deferred to the proxy layer (`proxy_wiring::evaluate_mtls`). The cluster
operational listener needs `.build()` without it. `build_from_routes`
reads `Route.mtls.ca_cert_pem` (`mtls.rs:115-118`), unrelated to a
cluster CA. This is a new code path.

**There is no hot-swap precedent to copy.** A rustls `ServerConfig` is
immutable once built (`listeners/tls/rustls/mod.rs:57-95`), and the
codebase's only handling of a changed client CA is to warn and require a
restart (`mtls.rs:16-19`, `reload.rs:90`). Story 9.3's revocation needs
an arc-swappable acceptor built here.

**AC #6 is a confused-deputy guard.** `Command` is one flat message
including `SHUTDOWN` and `BAN_IP` (`lorica-command/proto/command.proto:14-59`)
with no plane discriminator. If the cluster bridge forwards rather than
strictly translating, any enrolled follower can shut down the control
plane's workers or poison its ban list.

**AC #4 exists because exact-version refusal makes rolling upgrades
impossible**: there is no order in which to upgrade nodes if a control
plane and a follower one patch apart cannot talk. Prost's unknown-field
tolerance is already the codebase's compatibility mechanism
(`command.proto:22-29`). Also note the reconnaissance angle: an
unauthenticated peer should not receive a build or protocol fingerprint,
hence the opaque pre-auth code.

**AC #7 is not a nicety.** One writer task drains one queue into one
stream (`rpc.rs:380-405`), with no chunking and no priority. A ~1 MiB
config or certificate push would block heartbeats behind it for the full
write, producing a false liveness timeout that triggers a reconnect that
drops the push.

**AC #8, the honest framing.** `EncryptionKey::encrypt` / `decrypt` are
generic and reusable for a non-certificate secret
(`lorica-config/src/crypto.rs:14-115`, ring AES-256-GCM,
`nonce||ct||tag`). But `load_or_create` (`crypto.rs:34-70`) writes 32 raw
bytes to a `0600` file at `<data_dir>/encryption.key`: no KDF, no
passphrase, no machine binding, no keyring. This epic promotes that file
from "this node's leaf keys" to "the identity root of the fleet", and
`docs/cluster.md` must say so. Story 9.1 AC #8 makes sure rotation
actually covers the new table.

**AC #9**: `RpcEndpoint` is one-shot per stream. On EOF the reader exits
and clears in-flight (`rpc.rs:475-487`); `Drop for Inner` aborts both
tasks (`rpc.rs:365-377`). Holders currently keep plain clones
(`startup/worker.rs:664-678`), which will not survive a reconnect.

**AC #10** prevents a restart stampede: after a control-plane restart
every follower reconnects within the backoff cap and each pulls
configuration plus certificates, a synchronised full-state burst against
a node that just started cold.

**AC #12**: the project's cardinality discipline is explicit
(`lorica-api/src/metrics.rs:17-18`, and every labelled counter carries a
written bound). A follower-controlled `node_name` as a label would let a
compromised node create unbounded series by rotating it on reconnect.

**Packaging: mostly already fine, and that is worth knowing.**
`dist/lorica.service:125` already has
`RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX AF_NETLINK`; 9444 is
above 1024 so `CAP_NET_BIND_SERVICE` (`:81-82`) suffices; the CA lands
under `ReadWritePaths=/var/lib/lorica` (`:72`); `SystemCallFilter` does
not block socket/listen/accept; and 9444 does not collide
(`cli.rs:22`, management 9443, proxy 8080/8443). No unit directive
changes are needed. What **is** needed: the postinst banners and usage
help that enumerate ports (`dist/build-deb.sh:121`, `:138-147`;
`dist/rpm/lorica.spec:57`, `:74-83`), the firewall stanza in
`docs/security/hardening-guide.md:32-44` (which currently DROPs 9443 and
needs an allow-enrolled-sources-only rule for the cluster port), and the
trust-boundary rewrite in `docs/security/threat-model.md:16,23,54,99`,
which today asserts "localhost only" and "no remote access".

Add a comment in the unit noting 9444 is opt-in and already permitted,
so a future hardening pass does not tighten `RestrictAddressFamilies`.

### Completion Notes

- **Phase 1 review decisions (2026-09-02)**, all within the
  established seam pattern, no AC text touched:
  - AC #2's "off unless a join token is live": token mint/verify is
    Story 9.3's contract, so 9.2 drives the enrollment listener's
    lifecycle from a token-liveness watch (open on >0 live tokens,
    auto-close on last burn/expiry) with the liveness source
    abstracted; 9.3 wires it to its token table. The lifecycle
    behaviour itself is fully testable in 9.2.
  - AC #7: the "separate credit over one connection" option is
    foreclosed by design - Story 9.1's QA documented the
    one-endpoint-one-FIFO contract in `lorica-command/src/rpc.rs`.
    9.2 takes the AC's second option: telemetry rides its own
    connection (own RpcEndpoint), config/control another.
  - AC #9's "cap scales with fleet size": the follower cannot know
    fleet size before connecting, so the handshake ack carries a
    fleet-size hint and the backoff cap derives from it (clamped,
    documented default when no hint yet).
  - Follower identity (client cert) is issued by 9.3's enrollment;
    9.2 proves the dialer against in-process listeners with fixture
    certs minted by the same CA code `cluster init` uses.
- **Implementation notes (2026-09-02)**:
  - Proto disjointness is PROVABLE, not just declared: ClusterFrame's
    oneof uses tags 101/102 against Envelope's 1/2, so cross-plane
    bytes decode to an empty kind (never a Command) - tested both
    directions including a worker SHUTDOWN. The bridge whitelist
    holds only Heartbeat in 9.2; every other body (or an out-of-phase
    Hello) is a protocol violation that drops the connection.
  - EKU split from 9.3 built now: serverAuth-only control-plane
    leaves, clientAuth-only node leaves; the integration tests prove
    each refuses the other role.
  - Schema policy: a follower BELOW the control plane's schema is
    refused SCHEMA_TOO_OLD; a follower AHEAD is admitted, so rolling
    upgrades have an order (followers first).
  - Enrollment listener binds `cluster port + 1` on the same host;
    its liveness source is a watch channel the control plane owns at
    0 - Story 9.3 publishes token counts on it. In 9.2 the socket
    therefore never opens in production, while the lifecycle is
    proven in-crate (open on >0, auto-close on 0, budgets counted).
  - Control-plane server leaf is minted per boot from the persisted
    CA (90 days >> process lifetime; nothing to persist or rotate).
    Missing CA or bad bind is fatal at startup: the operator asked
    for the plane.
  - Admission: permit held from TLS accept through serve_hello
    (convergence = handshake in 9.2; 9.4 must extend the hold across
    the initial config pull). Defaults 32 concurrent / 128 queued /
    retry-after 5 s.
  - Dialer backoff: equal-jitter exponential, cap =
    min(default_cap + fleet_hint s, 300 s), hint refreshed from
    HelloAck and HeartbeatAck; RETRY_LATER's retry_after_s overrides
    the next delay. Jitter via a tiny xorshift (no rand dependency).
  - Metrics bridge: lorica-cluster stays free of the Prometheus
    dependency and exposes monotonic atomics; lorica-api delta-syncs
    them into `lorica_cluster_rpc_total` and
    `lorica_cluster_preauth_rejections_total` at scrape time, plus a
    `lorica_cluster_enrollment_listener_open` gauge.
    `lorica_cluster_connection_state{node_id,state}` and
    `lorica_cluster_rpc_duration_seconds` are registered (contract
    stable from v1.7.0) and populate in 9.3 once server-side node
    identities exist.
  - Reuse of `x509-parser` via rcgen's feature: the crate was already
    in the tree through lorica-api, no new dependency.
  - Test hygiene lesson recorded: two mTLS integration tests
    deadlocked for hours (one-shot server waiting for client EOF
    while the test held the client endpoint and awaited the server).
    Every cross-task await in cluster tests now sits under a 10 s
    timeout so a regression fails fast instead of hanging CI.
- **Handoffs**: 9.3 - token liveness publisher, roster-driven
  fleet_size, node_id metric series + duration histogram, CRL
  rebuild through SwappableAcceptor, PKI test helpers worth folding
  into `tests/common/`; 9.4 - hold the admission permit across the
  initial config pull, the dialer must keep its incoming-request half
  (server-initiated pushes); 9.6 - telemetry gets its own Dialer
  instance (separate connection, AC #7's chosen option).
