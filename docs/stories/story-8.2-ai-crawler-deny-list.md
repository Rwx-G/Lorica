# Story 8.2: AI-Crawler (LLM) Deny-List

**Epic:** [Epic 8 - Multi-User RBAC, AI Bot Defense & Zero-Downtime Upgrades (v1.6.0)](../prd/epic-8-v1.6.0.md)
**Status:** InProgress
**Priority:** P0
**Depends on:** Story 8.1 (foundation module split + `check_<name>` filter convention + `dispatch_order_locked` regression pin) ; existing `lorica/src/bot_rdns.rs` rDNS resolver (forward-confirm reuse) ; existing per-route hot-reload pipeline.
**Author:** Romain G.

---

As an infrastructure engineer,
I want a first-class deny-list for AI / LLM crawlers (GPTBot, ClaudeBot, CCBot, PerplexityBot, Bytespider, ...) with User-Agent matching and rDNS forward-confirmation,
so that I can opt my routes out of LLM training scrapes without hand-rolling WAF custom rules and without false-positive blocking of legitimate Googlebot / Bingbot.

## Acceptance Criteria

1. New module `lorica/src/ai_bot.rs` carrying a curated `AiCrawler` registry. Each entry: `{name: &'static str, user_agent_pattern: &'static str, verification: Verification}` where `Verification` is one of `Rdns(&'static [&'static str])`, `IpRanges(&'static str)` (key into a `Lazy<HashMap<&'static str, Vec<IpNet>>>` populated from compile-time `include_str!`-ed vendor JSON files), or `UaOnly`. Per-vendor `Verification` choice driven by what the vendor actually publishes (verified 2026-05-03 against vendor docs - see Dev Notes "Vendor verification matrix") : `Rdns` for CCBot (`.crawl.commoncrawl.org`) and Applebot/Applebot-Extended (`.applebot.apple.com`) ; `IpRanges` for GPTBot, ChatGPT-User, OAI-SearchBot (OpenAI JSON), ClaudeBot/Claude-User/Claude-SearchBot (Anthropic `bots.json`), PerplexityBot/Perplexity-User, Amazonbot, and Meta crawlers (AS32934 ranges) ; `UaOnly` for Bytespider and Diffbot (no published verification mechanism). Registry sourced from the `ai-robots-txt/ai.robots.txt` community list as the UA-pattern starting point ; ships with at minimum 12 entries: GPTBot, ChatGPT-User, ClaudeBot, anthropic-ai (legacy), CCBot, PerplexityBot, Bytespider, Google-Extended (UaOnly - robots.txt token only, not a distinct fetcher), Applebot-Extended, Amazonbot, FacebookBot/facebookexternalhit, Diffbot. Vendor IP-list JSON content bundled at compile time via `include_str!` from `lorica/src/ai_bot/vendor_ips/<vendor>.json` ; each bundled file's header carries the source URL and the fetch date.
2. Per-route `ai_bot_policy: Option<AiBotPolicy>` field with three modes: `Off` (default, no behaviour change), `Deny` (return 403 + `Retry-After: 86400` + body : operator-configured HTML via existing `Route.error_page_html` if set, else a hardcoded plain-text fallback explaining the policy ; mirrors the existing `with_html` pattern used by other `Decision::reject` sites in `proxy_wiring/filters/`), `Log` (allow + structured-log + Prometheus counter).
3. Per-crawler verification dispatches on the `Verification` variant: `Rdns(suffixes)` does forward-confirmed rDNS via `lorica/src/bot_rdns.rs` (cache-hit path stays sub-millisecond, NOT a separate `lorica-rdns` crate - none exists) ; `IpRanges(vendor_key)` does an O(log N) CIDR-membership lookup against the bundled list ; `UaOnly` skips verification (UA match alone is the signal). On verification failure (rDNS mismatch or IP outside ranges), apply the spoofed-fallback. Per-route override `Route.ai_bot_spoofed_fallback: Option<SpoofedFallback>` falls back to `GlobalSettings.ai_bot_treat_spoofed_as` (default `Deny`) when `None`. The `SpoofedFallback` enum has variants `Deny`, `Log`, `Allow`. The fallback only applies to `Rdns` and `IpRanges` crawlers - `UaOnly` matches go straight to the per-route `policy` (no spoof check possible without a published vendor signal).
4. Two Prometheus counters: `lorica_ai_bot_total{crawler, route_id, action="deny|log|spoofed|ua_only_match"}` (the `ua_only_match` action surfaces hits on `Verification::UaOnly` crawlers - operator monitors signal quality, since UA-only entries are spoof-trivial) and `lorica_ai_bot_rdns_unavailable_total` (no labels, operator-visibility for the rDNS resolver-disabled fail-open path). Cardinality bounded by `crawler_count * route_count * 4` for the first counter. Registered through the existing `lorica-api/src/metrics.rs` `REGISTRY` (no `lorica-metrics` extraction prerequisite - see Dev Notes).
5. Dashboard route drawer Protection tab gains an "AI crawler policy" section: dropdown (Off / Deny / Log) + spoofed-fallback dropdown + a "Detected crawlers" widget pulling the last 24h from the counter (top-5 by hit count).
6. Settings page gains a global "AI crawler registry" tab showing the 12+ built-in definitions (read-only, displaying name + UA pattern + verification kind + source) AND a "Custom crawlers" sub-section: full CRUD on operator-defined entries with `name`, `user_agent_pattern` (regex, validated server-side with size + dfa caps), `verification` (a JSON object: `{"kind": "rdns", "suffixes": [".x.com", ".y.com"]}` OR `{"kind": "ip_ranges", "cidrs": ["1.2.3.0/24", "2001:db8::/32"]}` OR `{"kind": "ua_only"}` ; CIDR list validated server-side via `ipnet` parsing ; suffix list non-empty for `rdns`. JSON blob aligns with the existing `path_rules` / `header_rules` / `traffic_splits` storage convention in the `routes` table), `enabled` toggle. Custom entries are merged with the built-in registry at request-evaluation time ; on conflict (same `name`), custom wins (lets operators override a built-in vendor's IP list when it goes stale before the next Lorica release).
7. New endpoints `GET / POST / PUT / DELETE /api/v1/ai-crawlers/custom` (Operator + SuperAdmin once Story 8.3 lands ; admin-only in v1.6.0 release if 8.3 ships after 8.2) backed by a new `ai_crawlers_custom` SQLite table. Pattern compilation errors return HTTP 400 with the regex error message. Plus a stats helper `GET /api/v1/ai-crawlers/stats?route_id={id}&window=24h` for the dashboard widget.
8. Per-route policy AND custom-crawler edits hot-reload through the existing two-phase commit path (no restart). White-box regression test mirrors Story 8.1's `cert_reload_commit_tests.rs` shape.
9. Documentation: new `docs/ai-crawlers.md` page covering the built-in registry, the custom-crawler operator workflow, the rDNS forward-confirmation logic, the false-positive policy (Googlebot is intentionally excluded - it is a search-index bot, not an LLM training bot), and the operator-tunables.
10. **Auto-generated `/robots.txt` endpoint** (industry-standard opt-out signaling, RFC 9309), per-route opt-in. Lorica serves `GET /robots.txt` from the merged registry (built-in + custom-enabled) when the matched route has `Route.serve_robots_txt: bool == true` (default `false` - pure opt-in, zero behaviour change for existing deployments ; routes that have not opted in continue to passthrough `/robots.txt` to backend as before). Output: one `User-agent: <name>` block + `Disallow: /` per crawler that has `ai_bot_policy != Off` on this route, plus a `User-agent: *\nAllow: /\n` fallback when no crawlers are active on the route. Response: `Content-Type: text/plain; charset=utf-8`, `Cache-Control: public, max-age=3600`, `# Generated by Lorica vX.Y.Z` header comment with the registry source pin. **No global toggle** - operators enable per-route to avoid a silent default-behaviour-change on upgrade.
11. **Verified-bot header injection upstream** (Cloudflare-style `cf-bot-management-score` analogue). When `check_ai_bot` resolves to Allow on a verified bot (`Verification::Rdns` confirmed OR `Verification::IpRanges` matched), inject `X-Lorica-Verified-Bot: <crawler_name>` and `X-Lorica-Bot-Verification: rdns|ip_ranges` into the upstream request before forwarding. `Verification::UaOnly` matches inject `X-Lorica-Bot-Verification: ua_only` so backends can distinguish trust levels. Behaviour gated by global setting `ai_bot_inject_headers: bool` (default `true`). Header names use the `X-Lorica-` prefix to avoid collision with Cloudflare's `cf-*` and any operator-managed `X-Verified-Bot`. Reuses the existing `RequestCtx.forward_auth_inject` pattern (cf. `lorica/src/proxy_wiring/context.rs:102` and `proxy_wiring.rs:3141` for the upstream-injection loop).

## Integration Verification

- **IV1**: A `curl -H "User-Agent: GPTBot/1.0" https://route` returns 403 with the explanation body when `ai_bot_policy = Deny` AND the source IP is in the bundled `vendor_ips/openai_gptbot.json` ; returns 200 when `policy = Off` ; returns 200 + structured log entry when `policy = Log`.
- **IV2**: A `curl -H "User-Agent: GPTBot/1.0"` originating from an IP NOT in the OpenAI bundled CIDR ranges is treated according to the resolved spoofed-fallback (per-route `Route.ai_bot_spoofed_fallback` overrides `GlobalSettings.ai_bot_treat_spoofed_as`, default `Deny`). A `curl -H "User-Agent: CCBot/2.0"` from an IP whose rDNS does not resolve under `*.crawl.commoncrawl.org` is treated identically (Rdns variant).
- **IV3**: A `curl -H "User-Agent: Bytespider"` from any IP triggers `lorica_ai_bot_total{action="ua_only_match"}` and applies the per-route `policy` directly (no spoof check possible for `UaOnly` crawlers).
- **IV4**: New `tests-e2e-docker/` profile `ai-bot-smoke` exercises the 3 verification variants (Rdns, IpRanges, UaOnly) x 3 policy modes (Off, Deny, Log) + spoof detection (~18 assertions) ; runs in both single-process and workers mode.
- **IV5**: `curl https://route/robots.txt` on a route with `serve_robots_txt=true` AND `ai_bot_policy=Deny` returns 200 + `Content-Type: text/plain` + body containing `User-agent: GPTBot\nDisallow: /` ; same route with `ai_bot_policy=Off` returns 200 + the `User-agent: *\nAllow: /\n` fallback ; on a route with `serve_robots_txt=false` (default), the request proxies to backend (404 if backend has none - confirms backward compat).
- **IV6**: `curl -H "User-Agent: CCBot/2.0"` originating from a CCBot-confirmed IP (mocked via integration test fixture) results in the backend receiving `X-Lorica-Verified-Bot: CCBot` and `X-Lorica-Bot-Verification: rdns`. With `ai_bot_inject_headers=false`, the headers are absent. A `Verification::UaOnly` match (Bytespider) injects `X-Lorica-Bot-Verification: ua_only` (no `X-Lorica-Verified-Bot` header - distinguishes trust level). **Trust-laundering defense** : a request `curl -H "User-Agent: SomeBrowser" -H "X-Lorica-Verified-Bot: GPTBot"` (client-supplied spoofed header) MUST result in the backend NOT receiving `X-Lorica-Verified-Bot` at all (the `insert_header` overwrite removes it ; non-bot requests do not push a value into `ctx.ai_bot_inject` so the loop yields nothing for the upstream).
- **IV7**: Custom-crawler CRUD round-trip via `/api/v1/ai-crawlers/custom` : `POST` a valid entry returns 200 + the created row ; `GET` lists it ; `PUT` updates pattern + verification ; `DELETE` removes it. Invalid POST cases : (a) regex `[invalid` returns 400 with the regex error, (b) regex matching `Mozilla/5.0` baseline UA returns 400 with the matched-baseline error, (c) `cidrs` array of 65 entries returns 400 with the "exceeds 64" error, (d) attempting POST when `count == 256` returns 400 with the cap error. After a valid POST, hot-reload commit fires (no restart) and `MergedCrawlersHandle.load()` reflects the new entry within < 1s.
- **IV8**: Dashboard widget rendering : the route drawer Protection tab "Detected crawlers" widget renders a top-5 table after issuing 10 mixed `curl` requests with various AI-bot UAs ; the Settings "AI crawler registry" tab read-only built-in table displays 12 rows with verification kind badges ; the "Custom crawlers" sub-section round-trips a Create / Edit / Delete cycle via the dashboard form (Vitest component + Playwright e2e if Lorica has a Playwright suite ; otherwise manual curl-driven backend assertions are acceptable).

## Out of Scope (deferred)

- **Vendor IP-list runtime refresh daemon** (proposed Story 8.13, v1.7.0+) : v1.6.0 bundles vendor IP-list JSON at compile time. Operators get fresh lists by upgrading to the next Lorica patch release, OR by overriding via Custom Crawlers (AC #6) - the operator can disable a stale built-in entry and add a Custom Crawler with the fresh CIDR list. Daemon-based periodic re-fetch from each vendor's published JSON URL is deferred to v1.7.0.
- **Audit-log integration** (Story 8.9 dependency) : AI bot deny / log decisions do NOT emit `lorica::audit` events in v1.6.0. Story 8.9 introduces the audit-log substrate ; if 8.9 lands in the same v1.6.0 release window, retrofit one `audit_log!(...)` call site at the decision point ; otherwise defer to v1.7.0.
- **RBAC tagging on `/api/v1/ai-crawlers/custom` endpoints** (Story 8.3 dependency) : v1.6.0 ships single-admin auth for these endpoints. Story 8.3 retags to Operator + SuperAdmin via `require_role!(...)` (one-line per endpoint).
- **Per-route bot category aggregation** (HAProxy-Enterprise-style "block all training bots" UX) : v1.6.0 treats each crawler as a separate registry entry. Category abstraction deferred to v1.7.0 if operator demand surfaces.
- **Operator-defined IP-list import for Custom Crawlers** : v1.6.0's Custom Crawlers AC #6 supports `verification: ip_ranges:<comma-separated CIDR>` typed manually. Bulk JSON file upload (e.g. for an internal scraping farm with a multi-thousand-IP block) deferred to v1.7.0.
- **Retroactive evaluation against access-log** (per Epic 8 PRD line 322) : custom crawlers added via POST apply to NEW requests only.
- **`Verification::Asn(u32)` variant** : Meta publishes AS32934 ranges via WHOIS, not a stable JSON URL. v1.6.0 ships the WHOIS-prefetched CIDR list as `meta_as32934.json`. Native ASN-membership (live BGP table lookup) deferred to v1.7.0+ if needed.
- **Worker-mode `PreparedReload` RPC payload growth bound** : AC #8 extends the supervisor's 2-phase commit `PreparedReload` to ship `ai_crawlers_custom` table rows to workers. Each row is ~500 bytes (name + UA pattern + verification JSON blob + timestamps). The RPC channel enforces `MAX_MESSAGE_SIZE = 1 MiB` hard cap (verified at `lorica-command/src/rpc.rs:57` and `lorica-command/src/channel.rs:34`) ; the `PreparedReload` frame ALSO carries every other reload field (routes, certs, settings, etc.) which leaves a practical custom-crawler ceiling **closer to ~500 entries depending on the rest of the payload** (not 1000 as a naive 500B*1000=500KB calc suggested). The AC #6 server-side `ai_crawlers_custom count <= 256` cap is below this ceiling with comfortable headroom for the rest of the reload frame. Operators hitting the 256-entry soft-cap should signal a v1.7.0+ chunked / diff-based registry RPC. Built-in registry stays compile-time-bundled, no RPC traffic.

### rDNS substrate (load-bearing correction vs the original PRD)

**The PRD AC3 references a `lorica-rdns` infrastructure as if it were a separate crate. It is NOT.** The rDNS resolver lives in `lorica/src/bot_rdns.rs` (binary-crate internal module). Story 8.2 reuses the existing API directly :

- `pub fn handle() -> Option<Arc<RdnsResolver>>` (lorica/src/bot_rdns.rs:315) - process-wide handle, set once at startup via `set_handle(...)`.
- `pub fn cache_check(&self, ip: IpAddr, now: i64) -> Option<Option<String>>` (line 225) - sync hot-path lookup. Outer `Option` is cache hit / miss ; inner `Option<String>` is confirmed name / NXDOMAIN.
- `pub fn try_spawn_resolve(self: &Arc<Self>, ip: IpAddr)` (line 183) - async fire-and-forget populate ; dedups concurrent calls for the same IP.
- `pub async fn resolve_and_cache(&self, ip: IpAddr) -> Option<String>` (line 238) - async block-and-resolve. **Do NOT use this on the hot path** ; reserved for cold-cache scenarios (e.g. cron-scheduled tasks, integration tests).
- `pub fn suffix_matches(confirmed_name: &str, suffixes: &[String]) -> bool` (line 288) - the standard suffix check ; case-insensitive, trailing-dot-tolerant. Already-tested with 5 unit tests under `bot_rdns::tests`.

The cache is a 16k-entry LRU keyed by client IP, TTL 1h, initialized at startup with `RdnsResolver::from_system_conf()` (reads `/etc/resolv.conf`). The Story 8.2 AI bot evaluator is the SECOND consumer of this resolver ; the first is the existing bot-challenge `bypass.rdns` category (cf. `docs/architecture/bot-protection.md`).

### Anti-spoof default rationale

Default `ai_bot_treat_spoofed_as = Deny` because the typical operator deploying Story 8.2 wants to block AI scrapes. A request claiming to be GPTBot but coming from an IP outside OpenAI's published `gptbot.json` ranges (`Verification::IpRanges`), or claiming to be CCBot but with rDNS not resolving under `*.crawl.commoncrawl.org` (`Verification::Rdns`), is by construction either (a) a misconfigured legitimate bot (rare - vendor infra is generally well-behaved and CDN-stable) or (b) a malicious spoofer. Operators with high-noise environments (false-positive rDNS misconfigs, vendor IP-list staleness between Lorica patch releases) can flip to `Log` (allow + record for later analysis) or `Allow` (allow + fall through silently to the next filter stage), globally via `GlobalSettings.ai_bot_treat_spoofed_as` or per-route via `Route.ai_bot_spoofed_fallback`. The fallback only applies to `Rdns` and `IpRanges` crawlers ; `UaOnly` crawlers (Bytespider, Diffbot, Google-Extended) have no spoof signal so the fallback is structurally inapplicable - operators must accept that UA spoofing defeats verification for those entries (industry-standard limitation : Cloudflare's ML fleet and HAProxy-Enterprise's vendor data feed are the only known mitigations and neither is available outside their proprietary stack).

### Industry context (why this design)

Survey of 9 reverse proxies / CDN platforms (2026-05-03) confirmed that all non-hyperscalers ship UA + rDNS-where-published (NGINX, Caddy, Traefik plugins via ai.robots.txt, HAProxy community recipes, CrowdSec base scenarios, Dark Visitors / Known Agents). Cloudflare and HAProxy Enterprise add proprietary verification layers (ML fingerprinting fleet / vendor data feed) - neither is available outside their stack. No surveyed open-source proxy ships a per-vendor IP-list fetcher daemon as a base feature ; that's deferred to v1.7.0 (proposed Story 8.13). Story 8.2's design (UA + Rdns + IpRanges with bundled JSON) sits between the "UA-only" common case (NGINX, Caddy default) and the "ML fleet" leader (Cloudflare), giving real crypto verification for ~10/12 crawlers without a runtime fetcher.
